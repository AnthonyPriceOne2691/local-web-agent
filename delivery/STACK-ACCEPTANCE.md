## Разбор: где эта процедура подвела

Записывать КАЖДЫЙ случай, когда приёмка показала зелено, а дыра была.
Формат: симптом → корневая причина → что добавлено в harness → как проверено.

### 2026-07-28 — waiver гейта был невыразим в CI, а diff-coverage мерил не то

Два случая одной природы, вскрытые поставкой `mypy-strict` (правки-типизация,
которые по определению трогают весь код, ничего не меняя по смыслу).

**(а) `okf_sync_gate`: waiver только через env.** Типизация тронула модули под
`implementation:` шести concept'ов — гейт справедливо потребовал обновить канон.
Но инварианты не менялись, и правка concept'ов была бы ложным «обновлено».
Единственный предусмотренный обход — `ALLOW_CANON_DRIFT=1`, то есть переменная
окружения: **в CI её задать нечем**, а локальный обход невидим ревьюеру. Значит
любая правка без смены смысла (формат, типы, логи) роняла бы PR, и единственным
способом «пройти» был бы обход гейта целиком.
*Усиление:* гейт читает строку `canon_drift_waiver: reason=… by=…` из
`delivery/active/STATUS.md` — она попадает в дифф, видна в PR и живёт ровно одну
поставку. env-вариант оставлен для локальных прогонов.

**(б) `check_diff_coverage`: мерил файлы вне измеряемого пакета.** Гейт уронил PR
на `scripts/okf_sync_gate.py` — harness-скрипте, правленном в той же поставке.
Он показан как «0%, не исполнялся тестами вовсе», хотя `coverage.json`
собирается через `--cov=app`: всё вне пакета в отчёт не попадает **по
построению**. То есть гейт сообщал не о дыре в тестах, а о собственной ошибке
области.
*Усиление:* список изменённых файлов фильтруется по `$COV_PKG` — меряем ровно
то, что измеряется. `COV_EXCLUDE_RE` остаётся для другого случая: код внутри
пакета, но вне юнит-покрытия по природе (`app/main.py`, обёртка Playwright).

**Общее:** оба раза гейт был технически прав и практически бесполезен — он
требовал невозможного (обновить канон, который не менялся) или сообщал о том,
чего не измерял. Признак такого класса дефектов: гейт стабильно красный на
изменениях, которые заведомо безопасны. Лечится не отключением, а сужением
области либо видимым waiver'ом.

### 2026-07-28 — сломанный YAML workflow прошёл мимо всех гейтов

- **Симптом:** после «починки» main-guard он всё равно падал на каждом push, а
  `gh workflow list` показывал его как **путь** (`.github/workflows/main-guard.yml`),
  а не как имя. Локально: `pre-commit` зелёный, `merge_guard` зелёный, мерж
  прошёл — и только `yaml.safe_load` вручную показал `ScannerError` на строке 41.
- **Причина (механизм):** в теле `gh issue create --body "…"` многострочный текст
  вышел из блочного скаляра `run: |` (строки без отступа), и файл перестал быть
  валидным YAML. **Ни один гейт не парсил конфиги**: все проверки смотрели на
  код (ruff/mypy/eslint) и на снимки, а `.github/workflows/*.yml`,
  `.pre-commit-config.yaml`, `*.json` не читал никто. GitHub при этом не падает
  громко — он просто «не видит» workflow и валит прогон.
- **Усиление:** в `.pre-commit-config.yaml` добавлены `check-yaml`, `check-json`,
  `check-merge-conflict` (pre-commit-hooks). Косметические `trailing-whitespace` /
  `end-of-file-fixer` **сознательно не включены**: они тронули бы 11 доков не по
  теме, а формат кода уже держат `ruff-format` и `prettier`.
- **Проверено воспроизведением:** сломанный файл (до фикса) `check-yaml` валит с
  указанием строки; после фикса все три workflow парсятся, хуков стало 20.
- **Урок в копилку к предыдущим двум:** каждый раз дыра была там, где артефакт
  *существовал*, но его никто не *исполнял/парсил*. Сначала спрашивай «кто это
  читает?», потом «зелено ли оно».

### 2026-07-28 — `ci-oracles: tooling` стоял в STATUS, а CI был красным 6/6

- **Симптом:** контур приняли, две поставки закрыли как done, в STATUS —
  `ci-oracles: tooling`. Проверка `gh run list` показала: **все шесть прогонов
  красные, с самого первого**. Джоба `gates` падала на первом же шаге
  (`pre-commit run --all-files` → mypy `INTERNAL ERROR`), из-за `-e` обрывала
  джобу, и шаги gate-coverage / secrets / baseline-ratchet / diff-coverage
  **не выполнялись ни разу**. `main-guard` падал по построению (гонял pre-commit
  без `backend/.venv` и `node_modules`) и открыл 3 ложных issue.
- **Причина (механизм):** в наборе не было oracle на **статус CI**. Всё, что
  проверял harness, гонялось локальными инструментами и локальным Python 3.14;
  `merge_guard` тоже (он симлинкует локальный venv в worktree). Расхождение с
  CI-окружением такой набор не видит **в принципе** — mypy падал только на 3.12.
  Плюс формулировка «CI настроен» подменила «CI зелёный»: наличие workflow-файла
  снова было принято за работающий гейт (тот же класс, что merge_guard 2026-07-27,
  только на уровень выше).
- **Усиление:**
  1. `scripts/lint/check_ci_status.sh` — гейт «последний прогон `quality` на
     целевой ветке зелёный», подключён в `merge_guard` **последним**. Нет `gh` /
     нет прогонов / прогон идёт → явный WARNING, а не тихое «зелено».
  2. mypy-хук переведён на один вызов на пакет (`pass_filenames: false`): пропало
     разбиение на пачки, локальный и CI-прогон стали идентичны.
  3. Python в CI выровнен с локальным (3.14) — расхождение версий было корневой
     причиной, а не случайностью.
  4. `main-guard` переведён на `workflow_run` после `quality`: он больше не
     воспроизводит окружение, а реагирует на результат (и не плодит дубли issue).
  5. `diff-coverage` впервые прогнан: нашёл `app/main.py` (уже в `omit` coverage,
     но гейт этого не знал) и `playwright_session.py` (28.9% — обёртка внешнего
     SDK). Оба внесены в `COV_EXCLUDE_RE` **с причинами**, печатаемыми на каждом
     прогоне; порог 70% для остальных остался жёстким.
- **Проверено воспроизведением:** `CI_REF=main check_ci_status.sh` на красном
  main → `FAIL` с ссылкой на прогон и текстом «красный CI = stop-gate»; на ветке
  без прогонов → WARNING, exit 0. То есть новый гейт ловит именно ту ситуацию,
  которая проехала мимо приёмки.

### 2026-07-27 — baseline из чужого кода выглядел бы как «гейт работает»

- **Симптом:** `--generate` для `silent-except` дал 180 файлов / 385 сайтов при
  82 модулях в проекте. Если бы никто не посмотрел в снимок, гейт остался бы
  зелёным навсегда: 168 записей — это `site-packages`, они не меняются.
- **Причина (механизм):** `check_ast_gate.py` перечисляет файлы через
  `Path.rglob`, а не `git ls-files` (как grep-гейты), и `SKIP_PARTS` не содержал
  venv. При `LINT_PY_SRC=.` (единственный способ покрыть и `backend/app`, и
  `cli/` одним корнем) внутрь области попал `backend/.venv`.
- **Усиление:** `SKIP_PARTS` += `/.venv/`, `/site-packages/`, `/node_modules/`;
  та же правка для jscpd (`-i`). В приёмку добавлен пункт «каждый гейт показал
  непустой **и осмысленный** набор файлов» — не только непустой.
- **Проверено воспроизведением:** снимок удалён и пересобран — 11 файлов /
  20 сайтов, все из `backend/app`; число согласуется с независимым источником
  (ruff `S110`/`SIM105` указывает на те же 5 модулей).

### 2026-07-27 — «гейт мержа развёрнут» ≠ «гейт мержа работает»

- **Симптом:** `merge_guard.sh` лежал на месте, `chmod +x` сделан, в чеклисте
  выглядел закрытым. Первый реальный прогон на живой ветке: 4 из 5 гейтов
  FAIL — `backend/.venv/bin/python: No such file or directory`.
- **Причина:** гейт проверяет слитое состояние в **свежем worktree**, а тулчейн
  (`backend/.venv`, `frontend/node_modules`) gitignored и там отсутствует. Хуки
  зовут интерпретатор по фиксированному пути. То есть скрипт был бы «красным
  всегда» — и первый же мерж прошёл бы мимо него как «ну он вечно падает».
- **Усиление:** в `merge_guard.sh` добавлен симлинк тулчейна из основного клона;
  в приёмку добавлено правило: **каждый гейт-скрипт обязан быть прогнан хотя бы
  раз на реальном входе**, а не только положен в репозиторий. Наличие файла —
  не доказательство работоспособности (тот же класс ошибки, что «зелёный гейт,
  который ничего не сканирует»).
- **Проверено воспроизведением:** заведена пробная ветка с коммитом, прогон
  `DRY_RUN=1 merge_guard.sh` → сначала 4 FAIL (воспроизведение), после правки —
  5/5 OK; ветка удалена, в main перенесён только фикс скрипта.

### 2026-07-27 — гейт ругался на сам harness

- **Симптом:** `config-access` падал на `check_ast_gate.py`, `okf_validate.py`,
  `okf_sync_gate.py` — «нарушение вне baseline».
- **Причина:** правило «настройка только через типизированный `config.X`»
  адресовано прод-коду, а гейт-скрипты по контракту CQG §6 читают `os.environ`
  (`LINT_PY_SRC`, `STRICT`, `BASE`, `OKF_BUNDLE`). При `LINT_PY_SRC=.` они попали
  в область правила.
- **Усиление:** в `check_grep_gate.sh` добавлен `TOOLING_RE` — harness исключён
  из области **всех** grep-правил, с причиной в комментарии. Занесение в
  baseline было бы хуже: снимок, который никогда не растает, врёт про долг.
- **Проверено:** прод-код по-прежнему сканируется (90 файлов), правило ловит
  реальное нарушение — `backend/app/contracts/rules/budget.py` остался в baseline
  с 2 записями, а не исчез вместе с исключением.
