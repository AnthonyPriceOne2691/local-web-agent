# Tasks

## Mini-spec (class S, §2.2)

**Проблема.** Хук `protect_main` (`scripts/hooks/protect_main.py`, Delivery §10.1)
блокирует опасные git-команды по регулярному выражению, применённому ко **всей**
строке команды с `re.DOTALL`. Из-за этого признаки из **разных** команд складываются
в ложное срабатывание: пуш ветки рядом с `pkill -f "uvicorn app.main:app"` даёт `-f`
из одной команды и `main` из другой, и хук читает это как force-push в main. За одну
сессию сработало трижды, в том числе на попытке задокументировать сам дефект.

**Почему это важно.** Ложное срабатывание вреднее пропуска: обойти его стоит ноль
(достаточно разбить составную команду на две), поэтому агент быстро учится не
воспринимать хук серьёзно — и тогда защита не работает и в настоящем случае.
Одновременно нельзя допустить обратного: **ослабления** проверки. Настоящий
force-push в main, удаление main на remote и `reset --hard origin/main` обязаны
блокироваться как раньше.

**Решение.** Разбирать команду по разделителям (`&&`, `||`, `;`, `|`, перевод строки)
и проверять **каждый сегмент отдельно**. Признаки внутри одной команды по-прежнему
складываются — а между командами больше нет.

**Готово, когда:**

- [x] P1: `protect_main.py` проверяет правила по сегментам; регрессия с
      `pkill -f "uvicorn app.main:app"` рядом с пушем ветки **проходит**.
- [x] P2: опасные команды по-прежнему блокируются — force-push в main/master (любой
      порядок флагов, `-f`/`--force`/`--force-with-lease`, любой remote), удаление
      main на remote (`--delete` и `:main`), `reset --hard origin/main`.
- [x] P3: тесты — обе половины кейсов: «должен **пропустить**» (обычный пуш `main`,
      пуш ветки, force-push **не**-main, слово `main` в соседней команде, пустая
      команда, не-наш JSON) и «должен **заблокировать**» (все из P2). Опасные строки
      собраны **из частей-констант**, иначе сам файл не пройдёт хук, когда его
      содержимое попадёт в командную строку.
      **Отклонение от эскиза:** файл лежит не в `scripts/hooks/`, а в
      `backend/tests/test_protect_main_hook.py`. Причина: `testpaths = ["tests"]`,
      поэтому тест в `scripts/` не собирался бы ни локально, ни в CI — то есть был бы
      «есть, но не гоняется». Хук вызывается процессом через stdin-JSON, так что
      проверяется настоящая граница, а не внутренняя функция.
- [x] P4: негативный контроль — на версии из `origin/main` падают **4** кейса:
      три ложных срабатывания и один **пропуск** опасного (`reset --hard
      upstream/master`: старое правило знало только `origin/`).
      Запуск: `PROTECT_MAIN_HOOK=<старый файл> pytest tests/test_protect_main_hook.py`
      — путь к хуку берётся из env именно для этой проверки.
- [x] P5: гейты зелёные: `pytest` (**266**), `ruff check`, `ruff format`, `mypy` strict
      (89 модулей), `check_module_size`, `delivery_check`, `okf_sync_gate`.

**Второй класс ложных срабатываний, найденный тестами P3.** Правило матчило цель
подстрокой (`\bmain\b`), поэтому force-push **своей же ветки** `fix/protect-main-segments`
блокировался: слово `main` стоит между дефисами и границы слова его пропускают. Поэтому
цель теперь определяется по **токену-ссылке** (`_names_protected_branch`): токен
разбирается как refspec (`+main:main`, `HEAD:main`) и сравнивается целиком либо по
суффиксу `/main` (`origin/main`, `refs/heads/main`). Ветка `feature/main` будет принята
за защищённую — осознанная ошибка в безопасную сторону.

**Правка scope (объявлена, не протащена молча).** `reset --hard` теперь блокируется для
**любого** remote (`upstream/master`, а не только `origin/main`). Это то же правило,
обобщённое с захардкоженного `origin/`, а не новое: старая версия пропускала команду,
которая уничтожает локальную работу ровно так же. Список запрещённых **действий** не
расширялся.

**Границы (что в поставку НЕ входит).**

- Не расширяю список запрещённых команд: поставка про ложные срабатывания, а не про
  новые правила. Новое правило = отдельное решение владельца.
- Не трогаю серверную защиту ветки (платная на приватном репо — остаток зафиксирован
  в `delivery/STACK-ACCEPTANCE.md` § Остатки).
- Не разбираю shell по-настоящему (кавычки, подстановки, here-doc): разделение по
  разделителям — эвристика, и она обязана ошибаться **в сторону блокировки**. Если
  сегментация не сработала, правило всё равно видит подстроку и блокирует.

## Проверка (verify)

1. `python scripts/hooks/test_protect_main.py` (или `pytest`) — зелёный.
2. Негативный контроль: вернуть несегментную проверку → тесты «должен пропустить»
   падают; вернуть правку → зелёные.
3. Живая проверка хука через stdin JSON: составная команда с `pkill -f` и пушем
   ветки → exit 0; force-push в main → exit 2 с внятным сообщением.
